# 02 — การเก็บข้อมูล, Parse, แยกงานใหม่/Follow-up, กันข้อมูลซ้ำ

> เอกสารนี้ตอบ 3 ข้อกังวลหลัก: **(1) เก็บถูกต้องไหม (2) รูปแบบจะตรงไหม (3) งานใหม่ vs follow-up ทำยังไง**

---

## 1. วิเคราะห์ข้อความจริงของเซลล์ (จากรูป 01, 02)

เซลล์ส่ง 1 รายงาน = **หลายข้อความต่อกัน** ไม่ใช่ข้อความเดียว:

```
[text]     หน้างาน : ใหม่
           ช่าง :แคน
           โทร :0897165403
           รายละเอียดหน้างาน : หน้างานนี้เข้ามาเจอช่องแคม...
           ตามต่อ : จบกระทิง
[image]    รูปหน้างาน 1–3 รูป (บางครั้งส่งหลายรูปพร้อมกัน = imageSet)
[location] "90 ซอย 3 ตำบลในเมือง อำเภอเมือง นครราชสีมา 30000 ..."
```

### ความไม่สม่ำเสมอที่เจอจริง (parser ต้องรองรับ)

| ฟิลด์ | ตัวอย่างจริง | ปัญหา |
|---|---|---|
| หัวข้อ | `หน้างาน : ใหม่`, `.หน้างาน : ใหม่` | มีจุดนำหน้า, เว้นวรรครอบ `:` ไม่เท่ากัน |
| ช่าง | `ช่าง :แคน`, `ช่าง :ช่างกวาง`, `ช่าง :ณรง` | บางคนใส่คำว่า "ช่าง" ซ้ำ |
| โทร | `0897165403` | ปกติดี แต่อาจมี `-` หรือเว้นวรรค → normalize |
| ตามต่อ | `7/10/69(2วัน)` | วัน/เดือน/ปี พ.ศ. 2 หลัก + จำนวนวันในวงเล็บ |
| | `15 ต.ค 69 10 วัน` | เดือนย่อภาษาไทย ไม่มีจุดท้าย |
| | `จบกระทิง` | **ไม่ใช่วันที่** แต่เป็นสถานะ "จบที่อื่น" + ชื่อคู่แข่ง (กระทิง) |
| location | `W2XG+253 ตำบล สุรนารี อำเภอเมือง...` | บางครั้งเป็น Plus Code, มีเว้นวรรคหลัง "ตำบล" |

### ฟิลด์ที่ลูกค้าต้องการ (รูป 04) vs ที่เซลล์ส่งอยู่จริง

| ต้องการ (รูป 04) | ส่งอยู่ตอนนี้? | ได้จากไหน |
|---|---|---|
| วันที่รายงาน | ✅ | `timestamp` ของ webhook |
| ลำดับรายการวิ่งงาน | ✅ | ระบบรันเลขให้ (รหัสงาน) |
| ชื่อลูกค้า | ⚠️ มีแต่ชื่อช่าง | เพิ่มฟิลด์ `ลูกค้า` |
| เบอร์โทร | ✅ | `โทร` |
| หน้างานใหม่/เก่า | ✅ | `หน้างาน` |
| อำเภอ ตำบล | ✅ ทางอ้อม | parse จาก address ของ location |
| ชนิดลูกค้า (เจ้าของ/ช่าง, เก่า-ใหม่) | ⚠️ บางส่วน | เพิ่มฟิลด์ / ระบบรู้เองว่าเบอร์นี้เคยมีไหม (ลูกค้าเก่า/ใหม่) |
| สถานะหน้างานปัจจุบัน / ขั้นตอนการดำเนินการ | ⚠️ อยู่ในรายละเอียด | เพิ่มฟิลด์ `ขั้นตอน` หรือดึงด้วย LLM |
| ผู้มีอำนาจตัดสินใจ | ❌ | เพิ่มฟิลด์ `ผู้ตัดสินใจ` |
| คาดการณ์วันที่จะสั่งสินค้า | ❌ | เพิ่มฟิลด์ `คาดสั่ง` |
| จำนวนครั้ง & วันที่ติดตามล่าสุด | ✅ | ระบบนับจาก follow-up |
| สถานะการจบงาน | ⚠️ ปนใน `ตามต่อ` | เพิ่มฟิลด์ `สถานะ` ชัดเจน |
| ภาพ 3 ภาพ | ✅ | image messages |
| โลเคชั่น | ✅ | location message |
| หมายเหตุ | ⚠️ | ฟิลด์ `หมายเหตุ` (ถ้ามี) |

**สรุป:** ถ้าใช้รูปแบบปัจจุบันอย่างเดียว จะได้ข้อมูลประมาณ 60–70% ของที่ลูกค้าต้องการ → ต้อง **ปรับ template เล็กน้อย** (เพิ่ม 3–4 บรรทัด) หรือใช้ LLM ดึงจากรายละเอียด (ไม่แม่น 100%)

## 2. Template ที่เสนอ (เปลี่ยนจากเดิมน้อยที่สุด)

### 2.1 งานใหม่

```
หน้างาน : ใหม่
ลูกค้า : คุณสมชาย (เจ้าของ)
ช่าง : แคน
โทร : 0897165403
ผู้ตัดสินใจ : เจ้าของบ้าน
รายละเอียดหน้างาน : ...
ขั้นตอน : ตั้งโครงแล้ว รอมุงหลังคา
คาดสั่ง : 20/10/69
ตามต่อ : 25/10/69
```
+ รูป 1–3 รูป + แชร์โลเคชั่น (เหมือนเดิม)

บรรทัดใหม่ทั้งหมด **ไม่บังคับ** — ถ้าไม่ใส่ ระบบยังบันทึกได้ แค่ฟิลด์นั้นว่าง และ bot จะบอกว่าขาดอะไร

### 2.2 Follow-up (ติดตามงานเก่า) — 2 วิธี

**วิธี A (แนะนำ, ง่ายสุดสำหรับเซลล์):** กดค้างที่ข้อความรายงานเดิม (หรือข้อความยืนยันของ bot) → **"ตอบกลับ"** แล้วพิมพ์:
```
อัปเดต : ช่างตั้งโครงเสร็จแล้ว รอเจ้าของบ้านกลับจากต่างจังหวัด
สถานะ : ตามต่อ
ตามต่อ : 30/10/69
```
→ webhook มี `quotedMessageId` → ระบบรู้ทันทีว่าเป็นงานไหน **แม่น 100%**

**วิธี B:** ใส่รหัสงานที่ bot ให้ไว้
```
ติดตาม : 691017-03
อัปเดต : ...
สถานะ : จบได้
```

### 2.3 คำสถานะมาตรฐาน (ต้องคอนเฟิร์มกับลูกค้า)

| สถานะ | คำที่ parser รับได้ | ฟิลด์เพิ่ม |
|---|---|---|
| `following` ตามต่อ | ตามต่อ, ติดตาม, รอ | วันที่ต้องตามต่อ |
| `won` จบได้ | จบได้, ได้งาน, ปิดได้, สั่งแล้ว | ยอดขาย (ถ้าต้องการ) |
| `lost` จบที่อื่น | จบที่อื่น, จบ{ชื่อคู่แข่ง} เช่น `จบกระทิง`, ไม่ได้งาน | **สาเหตุ** + คู่แข่ง |
| `cancelled` ยกเลิก | ยกเลิก, ไม่ทำแล้ว | สาเหตุ |

ลูกค้าต้องการ "สาเหตุของงานที่จบที่อื่น" → ควรมีรายการสาเหตุมาตรฐาน (ราคาแพงกว่า, ช่างมีเจ้าประจำ, ของไม่พร้อม, ส่งช้า, ...) แล้วให้ parser/แอดมินจัดหมวด

## 3. การรวมหลายข้อความเป็น 1 รายงาน (Report Bundling)

ปัญหา: text, รูป, location มาเป็นคนละ webhook event และอาจมาไม่เรียงกัน

**กติกา (เก็บ state ใน Redis key `bundle:{groupId}:{userId}`):**

1. ข้อความ text ที่มีหัว `หน้างาน :` หรือ `ติดตาม :` หรือเป็นการ quote → **เปิด bundle ใหม่** (ปิด bundle เก่าของคนเดิมถ้ามี)
2. image / location จาก **คนเดียวกัน** ภายใน **10 นาที** หลังเปิด → แนบเข้า bundle
3. image / location ที่มา **ก่อน** text (ภายใน 5 นาที) และยังไม่มีเจ้าของ → ดึงเข้า bundle ที่เพิ่งเปิด (look-back)
4. ปิด bundle เมื่อ: หมดเวลา 10 นาที / คนเดิมเปิดรายงานใหม่ / ได้ location แล้วและรูปครบตาม `imageSet.total`
5. รูป/location ที่ไม่มีเจ้าของ → **orphan** → เข้าคิวรอตรวจ
6. ข้อความคุยเล่น/สติกเกอร์ที่ไม่มีหัวรายงาน → เก็บ raw อย่างเดียว ไม่สร้างรายงาน

> หมายเหตุ: เซลล์ 2 คนส่งพร้อมกันไม่ปนกัน เพราะ bundle แยกตาม `userId`

## 4. Parser (ชั้นแปลงข้อความ → ฟิลด์)

### 4.1 Rule-based (หลัก — เร็ว, ฟรี, ตรวจสอบได้)

- Normalize: ตัด `.` / `•` นำหน้าบรรทัด, แปลง `：` เป็น `:`, ตัดช่องว่างซ้ำ, แปลงเลขไทย ๐-๙ → 0-9
- แยก `key : value` ด้วย regex `^\s*[.\-•]*\s*(?P<key>[^:]{1,25}?)\s*:\s*(?P<val>.*)$` แล้ว map key ด้วย **พจนานุกรมคำพ้อง**
  - `หน้างาน` → site_type, `ช่าง` → contractor_name (ตัดคำว่า "ช่าง" ซ้ำ), `โทร|เบอร์|tel` → phone, `รายละเอียด(หน้างาน)?` → detail (รองรับหลายบรรทัดจนเจอ key ถัดไป), `ตามต่อ|นัด` → follow_up, `สถานะ` → status, `ผู้ตัดสินใจ|ผู้มีอำนาจ` → decision_maker, `คาดสั่ง` → expected_order_date, `ติดตาม|รหัส` → site_code
- **Phone:** ตัดทุกอย่างที่ไม่ใช่ตัวเลข, รับ 9–10 หลัก, `+66` → `0`
- **Thai date** (`pkg/thaidate`):
  - `d/m/yy` → yy < 100 คือ พ.ศ. 2 หลัก → 2500+yy−543 (69 → 2026)
  - `d เดือนย่อ yy` → map `ม.ค|ก.พ|มี.ค|เม.ย|พ.ค|มิ.ย|ก.ค|ส.ค|ก.ย|ต.ค|พ.ย|ธ.ค` (มี/ไม่มีจุดท้าย)
  - `(2วัน)` / `10 วัน` → เก็บเป็น `follow_up_in_days` เพื่อเช็กความสอดคล้อง
  - ถ้า value ขึ้นต้นด้วย `จบ` → **ไม่ใช่วันที่** → status = won/lost ตามคำ, ส่วนที่เหลือ (`กระทิง`) = competitor
- **Address จาก location:** regex `ต(?:ำบล|\.)\s*(\S+)` และ `อ(?:ำเภอ|\.)\s*(\S+)`, จังหวัดจากคำหลัง อำเภอ, รหัสไปรษณีย์ 5 หลัก
  - ทางเลือกแม่นกว่า: ใช้ **PostGIS + shapefile ขอบเขตตำบล** หา point-in-polygon จาก lat/lng (ไม่พึ่ง text)

### 4.2 LLM fallback (ทางเลือก — เปิดเมื่อต้องการ)

- ใช้เมื่อ rule-based ได้ฟิลด์ไม่ครบ หรือต้องดึงของที่อยู่ใน "รายละเอียด" (ผู้ตัดสินใจ, ขั้นตอน, สาเหตุจบที่อื่น)
- เรียก Claude Haiku / Gemini Flash พร้อม JSON schema บังคับ output, ส่งเฉพาะ text (ไม่ส่งรูป) → ต้นทุนต่ำมาก
- เก็บ `parsed_by = rule|llm` และ `confidence` ไว้ทุกฟิลด์ — ฟิลด์จาก LLM ที่ confidence ต่ำ → รอตรวจ

### 4.3 ผลลัพธ์ parse

```json
{
  "site_type": "new",
  "contractor_name": "แคน",
  "phone": "0897165403",
  "detail": "หน้างานนี้เข้ามาเจอช่องแคม...",
  "status": "lost",
  "competitor": "กระทิง",
  "follow_up_date": null,
  "missing": ["customer_name", "decision_maker"],
  "confidence": 0.92
}
```

## 5. งานใหม่ vs Follow-up และการกันข้อมูลซ้ำ (Site Matching)

แนวคิด: แยก **"หน้างาน (Site)"** ออกจาก **"รายงาน (Report)"**
- 1 Site มีได้หลาย Report (ครั้งแรก + follow-up หลายครั้ง) → ได้ timeline แบบคอลัมน์ "รายละเอียดหน้างาน" ใน Excel เดิม (`17.08 ... 22.08 ... 25.08 ...`)
- 1 Contact (เบอร์โทร) มีได้หลาย Site (ช่าง 1 คนรับหลายหน้างาน) → **เบอร์โทรอย่างเดียวระบุหน้างานไม่ได้**

### ลำดับการจับคู่ (หยุดที่ข้อแรกที่ match)

| # | สัญญาณ | ความมั่นใจ | ผล |
|---|---|---|---|
| 1 | `quotedMessageId` ชี้ไปที่รายงานเดิม / ข้อความ bot | 100% | follow-up ของ site นั้น |
| 2 | มีรหัสงาน `691017-03` ที่มีอยู่จริง | 100% | follow-up |
| 3 | เบอร์โทรตรง + site นั้นยังเปิดอยู่ + มีแค่ 1 site | สูง | follow-up (auto) |
| 4 | เบอร์ตรง แต่มีหลาย site เปิดอยู่ → ใช้ location ใกล้สุด ≤ 150 ม. | สูง | follow-up (auto) |
| 5 | location ห่างจาก site ที่ยังเปิด ≤ 150 ม. แต่ **เบอร์ต่างกัน/ไม่มีเบอร์** | กลาง | **รอตรวจ** — กรณี "เจอหน้างานเดิมแต่คนละช่าง" (ข้อกังวลในรูป 04) |
| 6 | เขียน `หน้างาน : เก่า` แต่หาไม่เจอ | ต่ำ | **รอตรวจ** |
| 7 | ไม่ match อะไรเลย + `หน้างาน : ใหม่` | — | สร้าง Site ใหม่ + รันรหัส |

**ระยะ 150 ม.** ปรับได้ใน config (ต่างจังหวัดบ้านห่างกัน อาจใช้ 100–200 ม.) — ใช้ฟังก์ชัน Haversine ใน Go หรือ PostGIS `ST_DWithin`

### กรณีพิเศษ

- **หน้างานเดิม เจอช่างใหม่** → Site เดิม, เพิ่ม Contact ใหม่ผูกกับ Site (Site ↔ Contact เป็น many-to-many พร้อม role: เจ้าของ/ช่าง)
- **เซลล์คนอื่นมาเจอหน้างานเดียวกัน** → แจ้งในคิวรอตรวจ "หน้างานนี้ เซลล์ A ดูแลอยู่" ให้หัวหน้าตัดสิน (สำคัญกับการวัดผลงานเซลล์)
- **รายงานซ้ำ** (ส่ง text ซ้ำ 2 ครั้ง) → กันด้วย hash(userId + text) ภายใน 30 นาที
- **Unsend** → soft-delete report และ re-calc site
- **Edit** → re-parse report เดิม (ไม่สร้างใหม่)
- **แอดมิน merge site** ได้ ถ้าภายหลังพบว่าซ้ำ (ย้าย reports ทั้งหมดไป site หลัก)

### รหัสงาน (Site Code)

ใช้รูปแบบเดียวกับคอลัมน์ `NO.` ใน Excel เดิม: `YYMMDD-NN` (ปี พ.ศ. 2 หลัก) เช่น `690825-01` → ทีมคุ้นอยู่แล้ว

## 6. Bot ตอบยืนยันในกลุ่ม (ใช้ Reply = ฟรี)

ตัวอย่างข้อความ reply หลังรับรายงาน:

```
✅ บันทึกงานใหม่ #691017-03
ช่างแคน · 089-716-5403 · ต.ในเมือง อ.เมือง
ตามต่อ: 25 ต.ค. 69
⚠️ ยังไม่มี: ผู้ตัดสินใจ, คาดสั่ง
```

```
🔄 อัปเดต #690825-02 (ครั้งที่ 4)
สถานะ: ตามต่อ → 30 ต.ค. 69
```

```
❓ ไม่แน่ใจว่าเป็นงานไหน — แอดมินจะตรวจให้
(หรือกด "ตอบกลับ" ข้อความงานเดิมแล้วส่งใหม่)
```

ข้อดี: เซลล์รู้ทันทีว่าบันทึกถูกไหม → แก้ไขได้ทันที = **ข้อมูลถูกต้องตั้งแต่ต้นทาง** และมีรหัสงานไว้ quote ตอน follow-up

ข้อควรพิจารณา: เพิ่มข้อความในกลุ่ม (ลูกค้าอยากเห็น activity ของกลุ่มอยู่แล้ว) — ทำเป็น config เปิด/ปิด และเลือกโหมด "ตอบเฉพาะเมื่อมีปัญหา" ได้

> replyToken ต้องใช้ภายในเวลาสั้น ๆ หลังได้ event → ตอบจาก text message ทันทีหลัง parse (ไม่ต้องรอรูป/location)

## 7. แจ้งเตือนวันที่ต้องตาม (Follow-up Reminder)

| วิธี | โควต้า | หมายเหตุ |
|---|---|---|
| **แนบใน reply** — เมื่อเซลล์ส่งรายงานแรกของวัน bot แนบ "วันนี้คุณมีงานต้องตาม 3 งาน: #… #… #…" | ฟรี | แนะนำเริ่มด้วยวิธีนี้ |
| **สรุปประจำสัปดาห์** push เข้ากลุ่มวันจันทร์ | ~64/เดือน (16 คน) | อยู่ใน Free |
| **Dashboard** รายการ "ครบกำหนด / เลยกำหนด" | ฟรี | หัวหน้า/น้าอรดู |
| push รายวันเข้ากลุ่ม หรือ 1:1 รายคน | 300–350+/เดือน | ต้อง Basic (1,280 บาท) / 1:1 ต้องให้เซลล์แอดเพื่อน OA ด้วย |

Scheduler (cron) ทุกเช้า 07:30: คำนวณ `next_follow_up_date <= today` และ `status = following` → เตรียมรายการไว้ใน Redis ให้ reply ดึงไปใช้ / แสดงบน dashboard / ทำ "งานเลยกำหนด" (overdue)

## 8. สรุป: ความถูกต้องของข้อมูลมาจาก 4 ชั้น

1. **Raw ครบ** — เก็บ webhook ดิบทุกตัว + รูปลง R2 ทันที → ไม่มีอะไรหาย, re-parse ได้
2. **Template + พจนานุกรมคำพ้อง** — รองรับการพิมพ์ไม่เป๊ะ
3. **Feedback loop ในกลุ่ม** — bot ตอบยืนยัน/บอกฟิลด์ที่ขาด, follow-up ใช้ "ตอบกลับ" หรือรหัสงาน
4. **Human-in-the-loop** — อะไรไม่ชัวร์ เข้าคิว "รอตรวจ" ให้แอดมินกด ผูกงานเดิม / สร้างใหม่ / ข้าม
